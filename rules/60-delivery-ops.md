## 測る対象

DORA は 2025年に従来の4指標へ **Rework Rate（手戻り率）** を加え、準指標として Reliability を置いた。
AI支援開発では**スループットは上がるが不安定性も上がる**。したがって個人開発で見るべきは
速度そのものではなく、**「速く出して、壊れず、壊れたらすぐ戻せているか」**。

| 指標 | 個人開発での見方 | 目標 |
|---|---|---|
| デプロイ頻度 | 週に何回出せたか | 週1回以上 |
| リードタイム | 着手からデプロイまで | 数日以内 |
| **変更失敗率** | デプロイ後に修正/revertが必要になった割合 | **15%以下** |
| **手戻り率** | 出した直後に直し続けている度合い | 増えていたら品質ゲートを疑う |
| 復旧時間 | 壊れてから戻すまで | 1時間以内 |

> **手戻り率が上がっているときは、速度が出ているのではなく G1〜G3 のゲートが機能していない。**
> ゲートを緩めるのではなく、ゲートを直す。

## DEV-01 ブランチとコミット（MUST）

- **MUST** `main` に直接コミットしない。作業ブランチを切る。
- **MUST** `main` は常にデプロイ可能な状態を保つ。
- **MUST** 1PR = 1目的。**生成コードと lockfile を除く差分が400行以内**。
  超える場合は G0 に戻って分割する（例外なし。[01-definition-of-done.md](01-definition-of-done.md) G0 と同一の規範）。
- **SHOULD** コミットメッセージは Conventional Commits（`feat:` / `fix:` / `refactor:` / `chore:` / `docs:` / `test:`）。
  **なぜ変えたかを本文に書く**（何を変えたかは差分を見れば分かる）。
  プレフィックスの誤りは実ユーザーに被害を与えないため MUST ではない。
- **SHOULD** ブランチは短命に保つ（数日以内にマージ）。長生きするブランチは統合コストを指数的に増やす。
- **MUST** エージェントを無人（ループ）で走らせる場合は、`main` の作業コピーとは別に
  **`git worktree` で作業ディレクトリを分離する**。1つのエージェントの編集が、
  別の作業やレビュー中のツリーに触れないようにする（[70-loop-engineering.md](70-loop-engineering.md) LOOP-02）。

## DEV-02 CI（MUST）

`main` へのPRと push で以下を実行する。**1つでも赤ならマージしない。**

```yaml
# 必須ジョブ
- typecheck        # tsc --noEmit
- lint             # eslint --max-warnings 0
- format:check     # prettier --check
- test             # vitest run
- build            # next build
- test:e2e         # playwright（mainへのPRとリリース前）
```

セキュリティ設定（[20-security.md](20-security.md) SEC-10/16）:

- **MUST** `pnpm install --frozen-lockfile`（CIがlockfileを再生成しない）
- **MUST** GitHub Actions を**コミットSHAでピン留め**
- **MUST** `permissions:` を最小化（既定 `contents: read`）
- **MUST** シークレットは必要なジョブにのみ渡す

## DEV-03 環境（MUST）

| 環境 | 用途 | データ |
|---|---|---|
| local | 開発 | ダミーデータ |
| preview | PRごとの確認 | ダミーデータ。**本番DBに接続しない** |
| production | 本番 | 実データ |

- **MUST** preview 環境から本番DB・本番の外部サービスに接続しない。
  誤って本番データを壊す事故が最も多いのがここ。
- **MUST** 環境変数は環境ごとに分離し、preview に本番のシークレットを渡さない。
- **MUST** 本番と同等の設定でビルドが通ることをCIで確認する。

## DEV-04 データベースの変更（MUST）

**DBマイグレーションはロールバックできない前提で設計する。**

- **MUST** マイグレーションは **後方互換**（旧コードが動いたまま適用できる）にする。
- **MUST** 破壊的変更は3リリースに分ける:
  1. **追加**（新カラムを nullable で追加、両方書く）
  2. **移行**（データを埋め、読み先を新カラムへ）
  3. **削除**（旧カラムを落とす）
- **MUST** 本番へ適用する前に、**本番相当のデータ量でマイグレーションを試す**。
- **MUST** 適用前にバックアップを取る／取れていることを確認する。
- **MUST** `DROP` / `TRUNCATE` / `DELETE` を含む変更は、実行前に必ず対象を `SELECT` で確認する。

## DEV-05 リリース（MUST）

1. `main` が緑
2. [checklists/release.md](checklists/release.md) を通す
3. デプロイ
4. **本番でクリティカルパスを1回手で通す**（スモークテスト）
5. **30分間エラー監視を見る**
6. 新規エラーが出たら **先に戻してから調査する**

- **SHOULD** 対応できない時間帯にリスクのあるリリースをしない。
  個人開発では作業時間が夜間・週末に偏るのが普通なので、**時間帯そのものを禁止しない**。
  やるなら feature flag を OFF のまま出し、対応できる時間に有効化する。
- **MUST** ロールバック手順が書かれており、実際に実行できることを確認済み。
- **SHOULD** 影響の大きい機能は feature flag の裏に置き、コードのデプロイと機能の公開を分ける。

## OPS-01 監視（MUST）

- **MUST** エラー監視（Sentry等）が本番で有効。**通知先が生きていることをテストイベントで確認済み**。
- **MUST** 構造化ログ（JSON）。リクエストID・ユーザーID・操作・結果を含む。
  **パスワード・トークン・個人情報の本文を含まない**（[20-security.md](20-security.md) SEC-73）。
- **MUST** DBのバックアップが有効で、**リストア手順を1度は実際に試している**
  （試していないバックアップは、バックアップがあるとは言えない）。
- **SHOULD** アップタイム監視（外形監視）。
- **SHOULD** 認可拒否の急増を通知（攻撃の兆候）。

## OPS-02 依存の更新（MUST）

- **MUST** 月1回、依存を更新して `pnpm verify` を通す。放置した依存はまとめて上げられなくなる。
- **MUST** `pnpm audit` の critical / high を残さない。
- **MUST** リリース遅延が3日以上に設定済み（SEC-11。**キー名と単位がpnpm/npmで異なる**ため、
  設定した気になるのではなく `pnpm config list | grep -i releaseAge` 等で解決値を確認する）。
- **SHOULD** Dependabot / Renovate を使い、**まとめて上げず**、パッチとマイナーを分ける。

## OPS-03 インシデント対応（MUST）

**壊れたときの順序を、壊れる前に決めておく。**

```
1. 止血     ── まず戻す（revert / feature flag OFF / ロールバック）。原因究明はその後
2. 影響把握 ── いつから、誰に、何が起きたか。データが壊れていないか
3. 通知     ── ユーザーに影響があったなら告知する。個人情報の漏えいなら法定の報告義務を確認
4. 原因     ── 落ち着いてから調べる
5. 再発防止 ── 「気をつける」で終わらせない。テストかゲートに変換する（原則 P6）
```

### 個人情報の漏えいが疑われる場合（MUST）

一定の漏えい等は、**個人情報保護委員会への報告と本人への通知が義務**。
自己判断で「大したことない」と処理しない。時間の制約があるため、
疑いを持った時点で要件を確認する。→ [50-japan-compliance.md](50-japan-compliance.md)

## OPS-04 記録を残す（SHOULD）

- `docs/decisions.md` — 技術選定と、その理由（1行でよい）
- `docs/runbook.md` — デプロイ手順、ロールバック手順、よくある障害と対処
- `docs/third-party.md` — 使っているサードパーティと、送信している情報（外部送信規律の公表事項と対応づける）

これらは「後で書く」と永久に書かれない。**該当する変更をしたPRの中で更新する。**

## OPS-05 エージェント実行の管理（MUST）

無人ループを使う場合、実行そのものを管理する。詳細は [70-loop-engineering.md](70-loop-engineering.md)。

- **MUST** すべてのループに turn上限を設定する（初期値5。LOOP-01）。
- **MUST** 同一の失敗が2回連続したら停止し、人間に戻す（LOOP-01）。
- **SHOULD** ループの実行ログ（何をturn上限まで回したか、最終的にどう停止したか）を残す。
  現時点では専用の保存先を持たない。障害調査が必要になった時点で `docs/runbook.md` に追記先を決める。
