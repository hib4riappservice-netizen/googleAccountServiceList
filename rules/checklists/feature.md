# チェックリスト: 機能完成時（G2）

機能を1つ作り終えたら、これを上から通す。**MUST 項目に1つでも欠けがあれば不合格**（実装継続）。

**このリストは「現時点で機械化できていないもの」を含む。** `pnpm verify` が実際に落とせるもの
（型エラー、lint、フォーマット、`test.only` 残留、テストの失敗）は緑であること自体が保証なので
載せない（[00-principles.md](../00-principles.md) P6）。それ以外は、**将来lint/CIに移せる見込みがあっても
今はまだ移せていないものを含めて**すべて載せる。

各項目に判定手段タグを付ける。

| タグ | 意味 |
|---|---|
| `[自動]` | 現在 `pnpm verify` または CI が実際に判定している |
| `[要自動化]` | 機械化できるはずだが、まだ仕組みが無い（対象コードが無い/未着手を含む） |
| `[人間]` | 設計判断・法的判断・視覚/操作の確認など、原理的に人間が必要 |

`[人間]` に該当する項目は [checklists/human.md](human.md) にも集約してある。
リリースのたびに132項目すべてを1人で通すのは非現実的なので、**`[人間]` はそちらで
まとめて確認してよい**（このファイルでは判定の完全性のために全項目を残す）。

`[要自動化]` は GitHub の [`要自動化` ラベル](https://github.com/hib4riappservice-netizen/01_xxx/issues?q=is%3Aissue+label%3A%22%E8%A6%81%E8%87%AA%E5%8B%95%E5%8C%96%22)
で追跡する。**タグを付けるだけで追跡先を持たないと、可視化されただけで解消されない**
（2026-08-13追記: 監査 loop-auditor-2 指摘E-2で発覚。当初は追跡先が存在しなかった）。
自動化を実装したら、対応するIssueをクローズし、タグを `[自動]` に更新する。

**[01-definition-of-done.md](../01-definition-of-done.md) G2 の MUST のうち、
`pnpm verify` で機械判定できないものを漏れなく含む。**
逆は不要 ── このリストにしかない項目は出典IDで規則本体に紐づいていればよい。
G2 を変更したら、同じPRでこのリストも更新すること。

**無印は MUST。SHOULD の項目には明示的に `(SHOULD)` と書く。**

コピーして使う。

---

## 0. 前提

- [ ] **`pnpm verify` が緑**（typecheck / lint / format / test / build。これで G1 は充足）`[自動]`
- [ ] デバッグコード・コメントアウトされた死んだコードを残していない `[人間]`

## 1. 仕様

- [ ] G0 で定義した Given / When / Then がすべて満たされている `[人間]`
  （テスト名をGWTと対応させれば部分的に裏付けられる。[30-testing.md](../30-testing.md) TEST-03）
- [ ] 満たせなかった条件がある場合、**明示して記録した**（黙って落としていない） `[人間]`
- [ ] 作った機能を1文で説明できる `[要自動化]`（`docs/specs/<slug>.md` の存在確認をCIスクリプト化できる）

## 2. 型

- [ ] 外部入力（フォーム / `searchParams` / `params` / ヘッダ / 外部API）が**境界でスキーマ検証**を通っている `[人間]`
  （「正しい境界で」の意味的な確認。`data/` が固まればlintで部分的に強制できる余地あり）
- [ ] `as unknown as T` を使っていない `[自動]`（`eslint.config.mjs` の `no-restricted-syntax`）
- [ ] 状態が判別可能なunionで表現され、**ありえない組み合わせが型として作れない** `[人間]`（設計判断）
- [ ] `@ts-expect-error` を使ったなら、理由コメントがある `[自動]`（`ban-ts-comment` / `minimumDescriptionLength`）

## 3. 権限（最重要）

- [ ] データの読み書きが **`server-only` な DAL 関数**を経由している `[人間]`
- [ ] DAL の外で DB パッケージ / `process.env` を import していない `[要自動化]`
  （[10-architecture.md](../10-architecture.md) ARC-01 が「機械的に検査できる」と明言している。
  `eslint-plugin-import` の `no-restricted-paths`、または `dependency-cruiser` で強制する。
  **`data/` が生まれた時点で必ず実装する** — 対象が無いのでまだ実装していない）
- [ ] DAL 関数の中で**認証**（誰か）を確認している `[人間]`
- [ ] DAL 関数の中で**認可**（このリソースの所有者か / 権限があるか）を確認している `[人間]`
- [ ] Server Action がページの `redirect()` に依存せず、**アクション経由でも認可が効く** `[人間]`
- [ ] クライアントに返るのが **DTO**（UIに必要なフィールドのみ）で、DBレコードそのままでない `[人間]`
- [ ] Client Component の props 型が広すぎない（`user: User` のようになっていない） `[人間]`
- [ ] Server Action の**戻り値**が最小限 `[人間]`

## 4. テスト

- [ ] 純粋なビジネスロジックにユニットテストがある `[人間]`（存在の網羅性）
- [ ] DAL / Server Action / Route Handler に統合テストがある `[人間]`
- [ ] **「他人のリソースを操作しようとすると失敗する」テスト**がある `[人間]`（各操作に1本あるかの網羅性。
  テスト自体の合否は緑/赤で`[自動]`だが、「必要な箇所すべてにあるか」は今のところ人間確認）
- [ ] バリデーションの境界値・不正入力のテストがある `[人間]`
- [ ] （バグ修正なら）修正前に失敗する回帰テストを**先に**書いた `[人間]`（順序の確認）
- [ ] クリティカルパスを変えたなら E2E を追加/更新した `[人間]`
- [ ] 追加したテストが単独実行でも通る（他のテストに依存していない） `[要自動化]`
  （CIで各テストファイルを個別実行するステップを足せば機械化できる）

## 5. 壊れ方

- [ ] loading の表示があり、**レイアウトが跳ねない** `[要自動化]`（CLSはLighthouseで測定可能。CI化は[checklists/release.md](release.md)側）
- [ ] empty の表示があり、**次の行動への導線**がある `[人間]`
- [ ] error の表示に3要素がある: ①何が起きたか ②次に取れる操作 ③（想定外なら）エラーID `[人間]`
- [ ] エラー時にスタックトレース / SQL / 内部パスがユーザーに露出しない `[要自動化]`
  （本番ビルドしたエラーページのレスポンスボディを検査するE2E/スクリプトで機械化できる。SEC-98と関連）
- [ ] 認可・検証の失敗が「拒否」に倒れている（フォールバックで通していない） `[人間]`
- [ ] 外部API呼び出しにタイムアウトがある `[人間]`
- [ ] `catch` して握りつぶしていない（するなら理由コメント） `[要自動化]`（ESLint `no-empty` 系ルールで空catchを検出できる。未設定）
- [ ] **決済・課金確定・メール送信・Webhook受信に冪等キーがあり、二重実行テストがある**（SEC-84） `[人間]`
  （二重実行テストの合否自体は`[自動]`だが、対象操作すべてに実装されているかは人間確認）

## 6. 観測

- [ ] 未捕捉例外がエラー監視に届く `[人間]`（監視サービスの選定・設定自体が未着手）
- [ ] 重要な操作（作成 / 更新 / 削除 / 課金 / 認証）が構造化ログに残る `[人間]`
- [ ] ログとエラー監視に **パスワード / トークン / APIキー / 個人情報の本文が入っていない** `[人間]`

## 7. 戻せる

- [ ] 1コミット or 1PRで revert できる `[人間]`
- [ ] DBマイグレーションがあるなら**後方互換**（旧コードでも動く） `[人間]`
- [ ] **生成コードと lockfile を除く差分が400行以内**（超えているなら G0 に戻って分割する。例外なし） `[自動]`
  （`pnpm check:diff-size`。PRで `.github/workflows/ci.yml` が自動実行する。
  550行のテスト差分で赤、50行で緑になることを隔離環境で実測確認済み）

## UIを変更した場合（追加）

- [ ] **Tabキーだけで一周した**（フォーカスが見える / 順序が視覚順と一致 / 罠にはまらない） `[人間]`
  （[40-frontend-ux.md](../40-frontend-ux.md)「自動チェックはWCAGの問題の一部しか検出できない」）
- [ ] フォーム項目に `<label>` が紐づいている（プレースホルダで代用していない） `[要自動化]`
  （axeの`label`ルールでカバーされる見込みだが、フォーム要素が無くまだ未検証。
  `jsx-a11y/label-has-associated-control`は未導入）
- [ ] エラーメッセージが `aria-describedby` で入力欄に関連づいている `[要自動化]`（axeで部分的に検証できるが未検証）
- [ ] 意味のある画像に代替テキスト / 装飾画像は `alt=""` / アイコンボタンに `aria-label` `[自動]`
  （`jsx-a11y/alt-text` を実装済み。`eslint.config.mjs` で実測確認: `eslint-config-next/core-web-vitals` にバンドルされている）
- [ ] テキストのコントラスト比 4.5:1 以上 `[自動]`（`tests/e2e/accessibility.spec.ts`。axe color-contrast。
  意図的な違反を注入して赤→緑を実測確認済み）
- [ ] タップ対象が 24×24px 以上 `[自動]`（同上のaxeスキャンに含まれる。target-size。該当要素が無いため未実証）
- [ ] sticky header にフォーカスが隠れない `[人間]`
- [ ] ドラッグ操作があるなら**ドラッグ以外の代替手段**がある `[人間]`
- [ ] 画像に width/height または aspect-ratio がある（CLS） `[要自動化]`（`next/image` 使用を前提に、生`<img>`をlintで検出できる）
- [ ] **375px 幅で崩れない / 横スクロールしない** `[自動]`（`tests/e2e/accessibility.spec.ts`。
  `overflow-x: hidden` が `scrollWidth` 判定を無効化することが判明したため、要素ごとの右端座標で検査する方式に修正。
  意図的な違反を注入して赤→緑を実測確認済み）
- [ ] クリック可能な要素が `<button>` / `<a>`（`<div onClick>` でない） `[要自動化]`
  （該当する`jsx-a11y`ルールは現状未導入）
- [ ] 確認ダイアログを置いたのは不可逆な操作（削除・解約・送金）のみ `[人間]`
- [ ] （クライアント遷移があるなら）遷移後に `<title>` が更新され、フォーカスが移る `[人間]`
