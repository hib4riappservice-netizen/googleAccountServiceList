# rules — 評価／合格基準と「正解の型」

Claude Code を使った Web アプリ個人開発における、**何をもって「できた」とするか**の定義。

- 対象スタック: **Next.js (App Router) + TypeScript**
- 想定規模: **一般公開・実ユーザーあり**（認証・個人情報・課金の可能性を含む）
- 策定日: **2026-08-11** / 根拠: [sources/](sources/)

---

## 使い方

### 1. セットアップ

`rules/` をプロジェクトに置き、`CLAUDE.md` をプロジェクトルートに配置する。

```bash
cp rules/CLAUDE.md ./CLAUDE.md
```

`CLAUDE.md` は意図的に短くしてある（**本プロジェクトの運用値として60〜80行**。
公式に行数の規定はなく、「短く簡潔に。行ごとに"これを消したら Claude が間違えるか"を問え。
肥大した CLAUDE.md は無視される」という定性的な指針が示されている）。
長い規約を全部 `CLAUDE.md` に詰めると、かえって守られなくなる。
詳細は必要なときに `rules/` を読ませる。

### 2. 開発サイクル

```
G0 着手前     受け入れ条件を Given/When/Then で書く。計画に合意する（plan mode）
              docs/specs/<slug>.md に永続化する
   ↓
  (無人ループで実行する場合のみ、ここに G-L が挟まる。
   停止条件・turn上限・作業場を先に決める。70-loop-engineering.md)
   ↓
G1 実装中     pnpm verify が緑になるまでが「実装中」
   ↓
G2 完了時     checklists/feature.md を通す（「正解の型」7項目）
   ↓
G3 リリース前 checklists/release.md を通す
   ↓
G4 リリース後 スモークテスト + 30分のエラー監視
```

### 3. 判定

| 状態 | 条件 |
|---|---|
| **合格** | 該当ゲートの MUST がすべて満たされ、落とした SHOULD に理由がある |
| **条件付き合格** | MUST は満たすが SHOULD に未対応。**課題として記録した場合のみ**可 |
| **不合格** | MUST に欠けがある |

> **「動く」は合格条件ではない。「動く・壊れない・戻せる・追える」で合格。**

## この基準の設計思想

### なぜ機械的ゲートを主軸に置くのか

DORA 2025 の調査によれば、AI支援開発は**スループットと正の相関**を持つ一方、
**変更失敗率・手戻り率の増加**とも相関する。原因は「AIがコード生成の速度を上げるが、
**レビューとデプロイの基盤がそれを吸収しきれない**」こと。AIは既存の強み・弱みの**増幅器**である。

個人開発ではレビュアーが自分1人しかいない。したがって
**人間の注意力を前提にした基準は必ず破綻する。**
このルール群が「型 → lint → テスト → CI」の順に落とすことを優先し、
チェックリストを最後の手段に置いているのはこのため（[00-principles.md](00-principles.md) P6）。
**同じ制約は、エージェントを無人ループで走らせるときにより強く効く**
（[70-loop-engineering.md](70-loop-engineering.md)）。

### なぜセキュリティを厚くしているのか

OWASP Top 10:2025 では **Broken Access Control が引き続き1位**、
**Security Misconfiguration が2位に上昇**、**Software Supply Chain Failures が新設で3位**。
つまり事故の重心は「巧妙な脆弱性」ではなく、**認可の抜け・設定ミス・依存パッケージ**にある。
どれも個人開発で最も起きやすく、かつ機械的に防ぎやすい。

### なぜ日本の法令を含めるのか

「個人開発だから適用されない」ということはない。特定商取引法・個人情報保護法は、
法人／個人を問わず営利目的でサービスを提供する事業者に適用される。
また**プライバシーポリシー・外部送信の公表・特商法表記は「公開の条件」**であって、
公開後のTODOではない。

## メンテナンス

- **DoD の MUST は、漏れなくチェックリストに現れること**（逆は不要。
  チェックリスト固有の項目は出典IDで規則本体に紐づける）。
  `01-definition-of-done.md` の MUST を追加・削除・変更したら、**同じPRで `checklists/` を更新する**。
  実際に運用時に読まれるのはチェックリストなので、ここが乖離すると **MUST が静かに消える**。
  チェックリストの各項目には出典ID（`〔SEC-92〕` のように）を書く。
- **`sources/` を直したら、そのファイルを根拠として宣言している本体ファイルを `grep` で洗う。**
  根拠だけ直して派生を直さないと、本体に古い（誤った）記述が残る。
- **同じ規範を2箇所に書かない。** 片方を「〜を参照」にして規範は1箇所に置く。
  表現がずれると、必ずどちらかが陳腐化する。
- ルールを変えるときは、**先に [sources/](sources/) に根拠を追記**してから本体を直す。
  根拠のないルールは、後で誰も判断を再現できない。
  **出典に実在しない記述を「公式が言っている」と書かない**（初版でこれをやって監査で落ちた）。
- チェックリストに項目を足したくなったら、まず **「これは型かlintにできないか」** を考える
  （[00-principles.md](00-principles.md) P6）。
- ルールが守られていないことが繰り返し起きたら、**ルールが悪いか、ゲートが機能していない**。
  「気をつける」で終わらせず、仕組みに変換する。
