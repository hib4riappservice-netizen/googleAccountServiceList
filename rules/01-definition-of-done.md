# 01. 合格基準 — Definition of Done

「できた」と言ってよい条件を定義する。**このファイルが評価の中心**。

## 表記

| 記号 | 意味 | 割り当ての基準 | 扱い |
|---|---|---|---|
| **MUST** | 必須 | **欠けると実ユーザーに被害が出る、または法令違反になる**もの | 1つでも欠けたら **不合格**。マージ・リリースしない |
| **SHOULD** | 推奨 | 品質・保守性に効くが、欠けても直接の被害には至らないもの | 満たさない場合は理由を残す。理由なく落とすのは不合格 |
| **MAY** | 任意 | 多層防御の追加層、好みが分かれるもの | 判断は状況次第。落としても記録不要 |

> **MUST を安易に増やさない。** すべてが MUST になると重みが失われ、
> 実際には「確認コストの低いもの」だけが守られ、認可テストやリストア試行のような
> **コストが高く重要なもの**から捨てられる。
> MUST を足したくなったら、まず「これが欠けたとき、実ユーザーに何が起きるか」を1文で書く。
> **書けないなら SHOULD。**
>
> MAY の例: `experimental.taint` の有効化（ARC-04）、branded type（TS-01）、
> pnpm の追加ハードニング（SEC-15）。いずれも多層防御の追加層であり、
> 無くても他の MUST が守られていれば事故にならない。

---

## ゲート構造

変更は5つのゲートを順に通る。**前のゲートを飛ばして次へ進まない。**

```
G0 着手前     ── 何を作るか合意する          （人間が判断）
  │
  │  G-L 実行中（無人ループの場合）── 停止条件と上限が定義されている
  │             [70-loop-engineering.md](70-loop-engineering.md)
  ↓
G1 実装中     ── ローカル自動チェックが通る   （機械が判断）
G2 変更完了時 ── 自己レビューを通る          （機械 + チェックリスト）
G3 リリース前 ── 公開の条件を満たす          （機械 + チェックリスト）
G4 リリース後 ── 壊れていないことを確認する   （観測）
```

G-L はゲートではなく **G0とG1の間で任意に挟まる実行方式**。人間が1回1回指示する場合は素通りする。

---

## G0: 着手前 — 何を作るか合意する

コードを1行も書く前に満たすこと。**適用範囲は、ユーザーから見える振る舞いを持つ
機能・修正**（Given/When/Thenが意味を持つもの）。`rules/`本体の改訂や
CI/ツール整備など、振る舞いを持たない変更には適用しない
（それらは[README.md](README.md)メンテナンス節の「根拠を先に書く」規律に従う）。

（2026-08-13追記: この境界を明記する前、`docs/specs/`永続化MUSTを新設した
本人（ルーブリック改訂とハーネス整備のPR群）が、その改訂PR自身にはspecを
書いていなかった。「新設したMUSTを新設した当人が守っていない」という自己矛盾として
監査（loop-auditor-2、指摘E-1）で発覚した。振る舞いを持たない変更にまで機械的に
Given/When/Thenを要求するのは元々無理があった、という判断のもとで適用範囲を絞った。
遡って書いた偽装のspecは作らない）

- **MUST** 作る機能が **1文** で言える。言えないなら分割する。
  - 注記: 差分を1文で説明できる程度に小さい変更（typo、ログ1行、変数名の変更）は、
    `sources/09-agentic-coding.md` の公式但し書き「差分を1文で説明できるなら計画は飛ばす」に従い、
    以下の G0 の残り項目（Given/When/Then の作成、`docs/specs/` への永続化）を省略してよい。
    この「1文」は計画を**スキップしてよい**基準であり、次項の「1文で言える」は計画に**進んでよい**基準で、
    両者は別の判定である。
- **MUST** **受け入れ条件が Given / When / Then 形式で書かれている**。最低1本、正常系と主要な異常系。
  - 例: `Given ログイン済みユーザー / When 自分の投稿の削除ボタンを押す / Then 投稿が消え、一覧に戻る`
  - 例: `Given ログイン済みユーザー / When 他人の投稿IDを直接POSTする / Then 403 が返り、データは変わらない`
- **MUST** G0の成果物（1文の説明、Given/When/Then、触るファイル、停止条件）を
  `docs/specs/<slug>.md` に**永続化する**（テンプレート: [../docs/specs/_template.md](../docs/specs/_template.md)）。
  **会話コンテキストにのみ存在する計画は G0 を満たさない。** `/clear` やコンパクションで消えるものを
  「合意した」とは呼ばない。
- **MUST** このタスクの**停止条件を、機械判定可能な形で1行書く**（例: `pnpm test` の該当ファイルが緑）。
  無人のループで実行する場合は、[70-loop-engineering.md](70-loop-engineering.md) LOOP-01 の turn上限も明記する。
- **MUST** 扱うデータに **個人情報・課金情報が含まれるか** を判定済み（含むなら [50-japan-compliance.md](50-japan-compliance.md) を先に読む）。
- **MUST** 変更範囲がレビュー可能な大きさ。**生成コードと lockfile を除く差分が400行以内**。
  超える場合は G0 に戻って分割する（**例外なし**。「分割すると壊れる」は分割単位の設計ミスであって免除理由ではない）。
- **SHOULD** 実装計画（触るファイル、DAL関数、テストの粒度）を先に出し、合意してから書き始める。
- **SHOULD** 「作らない」判断を検討した（既存機能・既存ライブラリで足りないか）。

> **Claude Code 運用**: G0 は plan mode で行う。計画が合意されるまで編集させない。
> 合意した内容は `docs/specs/` に書き出してから実装に入る（ループで実行する場合は必須）。

## G1: 実装中 — ローカル自動チェック

以下がすべて緑。**1つでも赤なら実装は継続中であり、完了ではない。**

- **MUST** `pnpm typecheck` — TypeScript エラー 0。`@ts-ignore` / `any` の新規追加なし
  （やむを得ない場合は `@ts-expect-error` + 理由コメント）
- **MUST** `pnpm lint` — エラー 0、警告 0
- **MUST** `pnpm format:check` — 差分なし
- **MUST** `pnpm test` — 全テスト green。**skip / only の残留なし**
- **MUST** `pnpm build` — 本番ビルドが通る

これらは1コマンドで走ること: `pnpm verify`

## G2: 変更完了時 — 「正解の型」を満たしているか

**1つの機能が完成した形**。これが本プロジェクトの正解の型であり、機能ごとにこの7点を確認する。

### 1. 仕様 — 受け入れ条件が満たされている

- **MUST** G0 で定義した Given/When/Then がすべて満たされている（テストで、または手動確認で）
- **MUST** 満たせなかった条件がある場合、それが明示されている（黙って落とさない）

### 2. 型 — 意味が型で表現されている

- **MUST** 外部入力は境界でスキーマ検証（Zod等）を通っている
- **MUST** `any` を使っていない。`unknown` から絞り込む
- **MUST** 状態は判別可能なunionで表現されている（`{ status: 'loading' } | { status: 'error', error: E } | ...`）
  - `isLoading` と `data` と `error` が独立に存在し、ありえない組み合わせが型として作れる状態は不合格

### 3. 権限 — 認可がDALに1箇所ある

- **MUST** データを読む/書く操作が **`server-only` な DAL 関数**を経由している
- **MUST** DAL 関数の中で **認証（誰か）と認可（このリソースを触ってよいか＝所有権）の両方**を検証している
- **MUST** Server Action は DAL に委譲し、アクション内でも認可が効いている
  （ページの `redirect()` に依存していない）
- **MUST** クライアントに返るデータが **DTO**（そのUIに必要なフィールドのみ）

### 4. テスト — 3層に存在する

- **MUST** 純粋なビジネスロジックに **ユニットテスト**
- **MUST** DAL / API ルートに **統合テスト**。特に **「他人のリソースを操作しようとしたら失敗する」テスト**
- **MUST** クリティカルパスを変更したなら **E2E** を追加/更新（[30-testing.md](30-testing.md) 参照）
- **MUST** 修正したバグには、**その修正前に失敗する回帰テスト**がある

### 5. 壊れ方 — 失敗系が実装されている

- **MUST** 非同期処理に loading / empty / error のUIがある
- **MUST** エラー時にスタックトレース・内部パス・SQLがユーザーに露出しない
- **MUST** エラー表示に次の3要素が含まれる:
  ① 何が起きたか ② ユーザーが次に取れる操作（再試行ボタン／問い合わせリンク）
  ③（想定外エラーなら）ログと突き合わせられるエラーID
- **MUST** 認可・検証の失敗は「拒否」に倒れる（フォールバックで通さない）
- **MUST** 決済・課金確定・メール送信・Webhook受信に**冪等キーがあり、二重実行テストがある**
  （[20-security.md](20-security.md) SEC-84）

### 6. 観測 — 何が起きたか分かる

- **MUST** 未捕捉例外がエラー監視に届く
- **MUST** 重要な操作（作成・更新・削除・課金・認証）が構造化ログに残る
- **MUST** ログとエラー監視に **パスワード・トークン・APIキー・個人情報の本文が入っていない**

### 7. 戻せる — 出したものを引っ込められる

- **MUST** 1コミット/1PRで revert できる
- **MUST** DBマイグレーションがある場合、**旧コードでも動く後方互換な変更**である
  （破壊的変更は「追加 → 移行 → 削除」の複数リリースに分ける）
- **SHOULD** 影響の大きい機能は feature flag の裏に置く

### 加えて、UI変更を含む場合

- **MUST** キーボードだけで操作を完走できる
- **MUST** フォーム項目に `<label>` が紐づいている
- **MUST** 意味のある画像に代替テキスト、装飾画像は `alt=""`
- **MUST** テキストのコントラスト比 4.5:1 以上（大きな文字は 3:1）
- **MUST** モバイル幅（375px）でレイアウトが崩れない

## G3: リリース前 — 公開の条件

**初回公開時は全項目、以降のリリースでは変更が触れた項目を確認する。**

### 品質

- **MUST** CI が全緑（typecheck / lint / test / build / E2E）
- **MUST** E2E のクリティカルパスがステージング相当環境で通る
- **MUST** Lighthouse（モバイル、3回実行の中央値）で **LCP ≤ 2.5s / CLS ≤ 0.1**、
  Accessibility スコア **90以上**
- **SHOULD** INP ≤ 200ms（**ラボ計測では算出できない**。実測が取れるまで判定対象外とし、
  代替として初期JS ≤ 200KB gzip を見る ── [40-frontend-ux.md](40-frontend-ux.md) PERF-01/PERF-03）

### セキュリティ

- **MUST** [20-security.md](20-security.md) の SEC-90〜SEC-98（本番設定）がすべて確認済み
- **MUST** SEC-99〜SEC-102（シークレット）がすべて確認済み
- **MUST** `npm audit` / `pnpm audit` に **critical / high の未対応がない**（例外は理由を記録）
- **MUST** SEC-11 のリリース遅延が**解決値の出力で**3日以上であることを確認済み
- **MUST** **認証・パスワードリセット・サインアップ・メール送信・課金・削除**の各エンドポイントに
  レート制限がある（SEC-40/41）
- **MUST** SEC-84 の冪等性が、決済・課金確定・Webhook受信に実装され、テストがある

### 法令・表記（日本）

- **MUST** プライバシーポリシーが公開され、フッターからアクセスできる
- **MUST** 解析ツール・広告タグを使うなら **外部送信に関する公表事項**が掲示されている
- **MUST** 有料課金があるなら **特定商取引法に基づく表記**がある
- **MUST** 利用規約が公開されている
- **MUST** 問い合わせ窓口がある
- **MUST** **アカウント削除導線が存在し、実際に動作する**（JP-02）
- **MUST** 開示・訂正・利用停止請求が来たときの処理手順が `docs/runbook.md` にある（JP-02）
- 詳細: [50-japan-compliance.md](50-japan-compliance.md)

### 運用

- **MUST** エラー監視が本番で有効かつ通知先が生きている（テストイベントを飛ばして確認）
- **MUST** DBのバックアップが有効
- **MUST** **リストア手順を1度は実際に試している**（OPS-01）
- **MUST** ロールバック手順が書かれている
- **SHOULD** アップタイム監視がある

## G4: リリース後 — 壊れていないことを確認する

- **MUST** デプロイ後、**クリティカルパスを本番で1回手で通す**（スモークテスト）
- **MUST** リリース後30分、エラー監視を見る。新規エラーが出ていたら **先に戻す**（調査は戻してから）
- **SHOULD** 主要指標（登録、主要アクションの成功率）が想定内

---

## 判定

| 状態 | 条件 |
|---|---|
| **合格** | 該当ゲートの MUST がすべて満たされ、落とした SHOULD に理由がある |
| **条件付き合格** | MUST は満たすが SHOULD に未対応がある。**未対応項目を課題として記録した場合のみ**可 |
| **不合格** | MUST に欠けがある。または「動くけどテストがない」「動くけどエラー時が未実装」 |

> 「動く」は合格条件ではない。**「動く・壊れない・戻せる・追える」が揃って合格**。
