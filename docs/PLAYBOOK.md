# 運用手順書 — 何をどの順番でやるか

**この文書はあなた（依頼者）が読むものです。**
gitやghのコマンドを覚える必要はありません。Claude Code に日本語で伝えれば実行されます。

前提知識は [OVERVIEW.md](OVERVIEW.md) にあります。

---

## 覚えるコマンドは5つだけ

| コマンド      | 何をするか                           | いつ                              |
| ------------- | ------------------------------------ | --------------------------------- |
| `claude`      | Claude Code を起動する               | 作業を始めるとき                  |
| `/grill-me`   | 考えを質問攻めにして整理させる       | 要件が固まっていないとき          |
| `/clear`      | 会話をリセットする                   | **機能が1つ終わったとき（重要）** |
| `pnpm dev`    | 開発サーバーを起動（画面を見る）     | 作りながら確認したいとき          |
| `pnpm verify` | 自己点検（型・書式・テスト・ビルド） | 「できた」と言う前                |

これ以外のコマンド（git、gh、テストの実行など）は**Claudeが代わりに実行します。**
「PRを出して」「マージして」と日本語で伝えれば通じます。

---

## 日常: 機能を1つ作る

### 手順

```
1. claude          ターミナルで起動
2. 「〇〇という機能を作りたい」と伝える
3. 質問に答える     ← ここが一番大事。あなたにしか答えられない
4. 仕様を確認して承認
5. 「実装して」
6. 「レビューして」
7. 「PRを出して」
8. CIが緑になったら「マージして」
9. /clear          次の機能へ
```

### 各段階であなたがやること

#### ステップ2〜4: 要件を決める（**あなたの仕事の中心**）

`spec-writer` が質問をまとめて投げてきます。**聞かれるのは「お金が関わる決定」
「個人情報の取扱い方針」「機械判定できない最終確認」の3種類だけです**
（`rules/00-principles.md` P9）。設計・実装・セキュリティの知識は前提にされません。
ライブラリ選定や実装方式のような技術的な選択肢を「どちらにしますか」と聞かれることは
ありません。それはエージェントが判断し、理由を `docs/decisions.md` に残します。

**答え方の例:**

```
Q1 → 推奨案でいい
Q2 → いや、こうしたい: ...
Q3 → 分からないので任せる
```

「分からないので任せる」は有効な回答です。ただし、聞かれる3種類の質問（お金・個人情報の
取扱い方針・最終確認）は**後から取り返しがつかないため、必ず自分で判断してください。**

最後に `docs/specs/機能名.md` というファイルが作られます。
**これに書かれていることが「完成の定義」です。** ざっと読んで、認識と合っているか確認してください。

> **なぜファイルに残すのか**: 会話は消えます。`/clear` したり日をまたいだりすると、
> Claudeは前の会話を覚えていません。ファイルに書いておけば、いつでも読み直せます。

#### ステップ5: 実装

Claudeが書きます。あなたは待つだけです。

途中で「〇〇してよいですか？」と聞かれたら答えてください。
特に**ファイルを消す・本番に触る**系の確認は慎重に。

#### ステップ6: レビュー

3体のレビュー担当が別々の観点で検査します（[AGENTS.md](AGENTS.md) 参照）。

**Critical / High の指摘は、あなたに見せる前にエージェントが直して再レビューします。**
あなたの画面に出てくる時点で、Critical / High は解消済みの状態です
（`rules/00-principles.md` P9）。指摘が出たら、**すべて直す必要はありません。**

| 指摘の重大度    | どうするか                               |
| --------------- | ---------------------------------------- |
| Critical / High | **直す**。特にセキュリティ関連           |
| Medium          | 直すか、なぜ直さないかを記録する         |
| Low             | 無視してよい。気になるなら課題として登録 |

> **なぜ全部直さないのか**: レビュー担当は「探せ」と言われれば何か見つけます。
> すべての指摘を潰そうとすると、不要に複雑なコードになります（公式ドキュメントも警告しています）。

#### ステップ7〜8: 提出と統合

「PRを出して」と言えば提出されます。GitHubが自動で検査（CI）を走らせます。

**3つの検査が全部緑になるまで統合できません**（GitHubがサーバー側で拒否します）。

赤くなったら、そのまま「直して」と伝えてください。

#### ステップ9: `/clear`

**機能が1つ終わったら必ず `/clear` してください。**

会話が長いほど、Claudeは過去のやり取りを読み返すことになり、費用が増えます。
`docs/specs/` にファイルが残っているので、忘れて困ることはありません。

---

## リリースする前に

機能がいくつか溜まって「公開しよう」となったら、
`rules/checklists/human.md` の**74項目**を確認します。

機械が見る項目は既にCIで通っているので、**ここに載っている項目だけ**見れば足ります。

特に飛ばしてはいけないもの:

- **バックアップから実際に復元できるか試したか**（試していないバックアップは無いのと同じ）
- **プライバシーポリシーの記載と、実際にやっていることが一致しているか**（法令違反になります）
- **キーボードだけで操作を完了できるか**（機械では検出できません）

公開した後は、**30分間エラーを見てください。** 異常があれば「戻して」と伝えます。
原因を調べるのは戻してからです。

## 困ったときは

| 状況                           | どうするか                                                  |
| ------------------------------ | ----------------------------------------------------------- |
| CIが赤い                       | 「CIが赤いので直して」と伝える。ログはClaudeが読みます      |
| 400行を超えたと言われた        | 「2つに分けて」と伝える。**ルールを緩めない**でください     |
| レビューの指摘が多すぎる       | 「Critical と High だけ直して」と伝える                     |
| 何をしていたか分からなくなった | 「今の状況を教えて」と聞く。`docs/specs/` も見てください    |
| Claudeが同じ失敗を繰り返す     | **2回で止める。** `/clear` して、指示を書き直す方が速いです |
| 費用が気になる                 | `/clear` の頻度を上げる。1機能=1会話が目安                  |

## 新しいサービスを立ち上げる

このリポジトリは**テンプレート（雛形）**です。複製して新しいサービスを作ります。

### 手順

**1. 複製する**（ターミナルで1回だけ）

```bash
gh repo create <サービス名> --template hib4riappservice-netizen/01_xxx --private --clone
cd <サービス名>
pnpm install
git config core.hooksPath .githooks
```

**2. Claude Code を起動して、初期設定を頼む**

```
claude
```

そして、こう伝えます。

```
新しいサービスのリポジトリを作った。以下をやってほしい:
- package.json の name をサービス名に変更
- README.md をこのサービス用に書き直す
- docs/specs/ の中身を空にする（テンプレート由来の仕様書を消す）
- docs/decisions.md をこのサービス用に初期化
- GitHub の branch ruleset で main を保護する
- pnpm verify が緑になることを確認する
```

**3. 最初の機能を作る**

あとは「日常」の手順と同じです。

### 引き継がれるもの・引き継がれないもの

| 引き継がれる                    | 引き継がれない                           |
| ------------------------------- | ---------------------------------------- |
| 品質基準（`rules/` 一式）       | 前のサービスのコード                     |
| AIエージェント5体（`.claude/`） | 前のサービスの仕様書                     |
| 自動チェック（`scripts/`、CI）  | GitHubの課題（Issue）                    |
| 説明書（`docs/OVERVIEW.md` 等） | branch ruleset（**手動で再設定が必要**） |

> **注意**: GitHubのテンプレート複製では、**branch ruleset（main保護）は引き継がれません。**
> 新しいリポジトリごとに設定し直す必要があります。上記の手順2に含めてあります。

---

## やってはいけないこと

| 禁止                        | 理由                                                               |
| --------------------------- | ------------------------------------------------------------------ |
| `main` に直接コミット・push | 検査を通らずに本番の枝が壊れる。フックとGitHubの両方で拒否されます |
| CIが赤いままマージ          | GitHubが拒否しますが、無理に回避しないこと                         |
| 400行ルールを緩める         | レビューできない大きさになります。「例外なし」と決めてあります     |
| `.env` ファイルをコミット   | 秘密情報が公開されます。フックで拒否されます                       |
| 「たぶん大丈夫」で公開      | 確認できていないことは、できていないことと同じです                 |

現在、点検項目132のうち**自動で守られているのは25項目（19%）だけ**です。

残り30項目は「自動化できるはずだが未実装」として
GitHubの課題（Issue #11〜#19、`要自動化` ラベル）に登録してあります。

**優先度が高いもの:**

1. **Issue #16** — リポジトリの履歴にシークレットが混入していないかの検査
2. **Issue #13** — エラー画面に内部情報が漏れていないかの検査
3. **Issue #11** — データ層の外からDBを直接触っていないかの検査（`data/` を作ったら必須）

公開前に決める必要があります（Issue #18）。
