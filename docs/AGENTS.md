# AIエージェント体制 — 誰が何をするか

このリポジトリには **5体のAIエージェント**が定義してあります（`.claude/agents/`）。
それぞれ役割が分かれていて、必要なときだけ呼び出されます。

前提として [OVERVIEW.md](OVERVIEW.md) の「4つの層」を読んでおくと理解しやすくなります。

---

## 5体の一覧

| エージェント         | 日本語で言うと       | いつ使うか           | 使うAI         | 権限         |
| -------------------- | -------------------- | -------------------- | -------------- | ------------ |
| `spec-writer`        | 要件定義担当         | 作り始める**前**     | 高性能（opus） | 全部         |
| `architect`          | 設計担当             | 実装を始める**前**   | 高性能（opus） | 全部         |
| `reviewer-security`  | セキュリティ検査官   | 実装が終わった**後** | 標準（sonnet） | **読むだけ** |
| `reviewer-checklist` | 点検リスト照合係     | 実装が終わった**後** | 標準（sonnet） | **読むだけ** |
| `test-auditor`       | テスト網羅性の監査役 | 実装が終わった**後** | 標準（sonnet） | **読むだけ** |

---

## 時系列で見た流れ

```
   あなた「こういう機能が欲しい」
        ↓
  ① spec-writer     曖昧さを質問で潰し、docs/specs/ に仕様を保存
        ↓
  ② architect       どう作るかを設計（DAL、型、エラー処理）
        ↓
     実装            ← エージェントを使わず、通常の対話で進める
        ↓
     pnpm verify     ← 機械。ここが赤なら先に進まない（AI費用ゼロ）
        ↓
  ③④⑤ レビュー3体   同時に走らせる。それぞれ別の観点で検査
        ↓
     PR提出 → CI → マージ
```

---

## なぜこの分け方なのか

### レビュー担当を分けている理由

**品質のためです。トークン節約のためではありません。**

`rules/70-loop-engineering.md` の LOOP-03 が
「実装したコードを、それを書いた本人が主観で判定しない」ことを**必須**としています。

自分が書いたコードを自分で採点すると、どうしても甘くなります。
別の視点（別の会話、別の判断基準）を挟むことで、これを防ぎます。

### レビュー担当が「読むだけ」の理由

3体のレビュアーには**ファイルを書き換える権限を与えていません**（`tools: Read, Glob, Grep, Bash`）。

理由は2つあります。

1. **役割の混同を防ぐ** — 指摘する人が勝手に直し始めると、何が問題だったのか分からなくなる
2. **費用を抑える** — 書き換えができないので、「直す→また確認する」の往復が発生しない

### 実装エージェントを作っていない理由

実装は**通常の対話で進めます。** 専用エージェントを作りません。

実装は「こう書いて」「いや、こうして」というやり取りが多く発生します。
エージェントに任せると、指示 → 実装 → 報告 → 修正指示 という往復が挟まり、
**かえって時間も費用もかかります。**

### テスト作成エージェントを作っていない理由

このプロジェクトはテストを先に書く方式（`rules/30-testing.md` TEST-06）です。
つまり**実装する人がテストも書きます。** 分けると二重管理になります。

ただし「**必要なテストが書かれていない**」という抜けは実装者からは見えにくいため、
`test-auditor` が事後に監査します。作るのと、抜けを探すのは別の仕事です。

## 使うAIの選び方

| 用途               | モデル               | なぜ                                                                   |
| ------------------ | -------------------- | ---------------------------------------------------------------------- |
| 要件定義・設計     | opus（高性能・高価） | 曖昧な要望を詰める、設計判断をする。**ここをケチると下流が全部壊れる** |
| レビュー           | sonnet（標準・安価） | 基準は文書に書いてある。それに照らすだけなので標準で足りる             |
| 型チェック・テスト | **AIを使わない**     | `pnpm verify` が確実かつ無料                                           |

---

## 費用を抑える工夫

1. **レビュー担当には変更部分（`git diff`）だけを渡す** — リポジトリ全体を読ませない
2. **レビュー担当は安いモデル + 読み取り専用** — 無駄な往復が起きない
3. **1機能=1PR=400行以内** — 1回の会話で完結し、過去のやり取りを読み返す量が減る
4. **機能の区切りで会話をリセット**（`/clear`）— 無関係な履歴を持ち越さない
5. **エージェントの本文にルールを書き写していない** — 各エージェントは `rules/` を
   その都度読みます。書き写すと二重管理になり、片方が古くなります

---

## 呼び出し方

**あなたが直接コマンドを打つ必要はありません。**

各エージェントの `description` に「いつ使うか」が書いてあり、
Claude Code がそれを読んで自動的に呼び出します。

明示的に指定したいときは、自然な日本語で伝えれば通じます。

- 「要件を詰めたい」→ `spec-writer`
- 「設計して」→ `architect`
- 「セキュリティ的に問題ないか見て」→ `reviewer-security`
- 「チェックリストを通して」→ `reviewer-checklist`
- 「テストの抜けを探して」→ `test-auditor`
- 「レビューして」→ 3体まとめて

---

## 注意点

**エージェントの判定は「合格証明」ではありません。**

`rules/70-loop-engineering.md` LOOP-04 が定めているとおり、
最終的な承認（Verdict）は**人間が持ちます。**

レビュー3体が「問題なし」と言っても、それは
「その観点では問題が見つからなかった」という意味であって、
`rules/checklists/human.md` の74項目が満たされたことにはなりません。

---

## この体制を変えるとき

エージェントを増やしたくなったら、まず次を考えてください。

1. **それは機械にできないか？** できるなら、スクリプトかCIにする方が安くて確実です
2. **既存の5体に含められないか？** 役割が増えるほど、どれを呼ぶべきかの判断が難しくなります
3. **実際に困ってから作る。** 「あった方がよさそう」で増やすと、使われないまま維持コストだけ残ります

この5体自体、**まだ実際の機能開発で使った実績がありません。**
使ってみて過不足があれば、そのときに調整するのが健全です。
