## 2026-08-16: UIデザインの見直しとExcel(.xlsx)出力の追加

CEOから「デザインが悪すぎる」「使い方の説明がない」「ボタンの間隔がおかしい」
「左下にIssueマークが出ている」「Excel出力ができない」という直接的なフィードバックを受けた。
P9に従い、実装方法は自分で判断して記録する。

- **「左下のIssueマーク」の正体はNext.js標準の開発者向けインジケータ**
  （`<nextjs-portal>`）だった。footerのリンクと重なって見えていた。
  `next.config.ts`に`devIndicators: false`を設定して無効化した（コンパイル/実行時
  エラーの表示自体は公式ドキュメント上、無効化されないと明記されている）。
- **同じ調査で見つけた副産物**: 開発モードのコンソールに`eval() is not supported`
  エラーが出ていた。CSPの`script-src`が`'unsafe-eval'`を許可していないため、
  Reactの開発時デバッグ機能（スタックトレース復元）がブロックされていた
  （本番ビルドはevalを使わないため実害は無い）。`NODE_ENV==='development'`の時だけ
  `'unsafe-eval'`を追加し、本番のCSPは変更していない。
- **UIを「スキャンボタン1個」から構造化**: ヘッダー（サービス名・タグライン）→
  できること（3行の説明、初見のCEOや将来の利用者が迷わないように）→
  サインイン/アカウント情報→スキャン、と`<section>`で明確に区切り、`--space-*`の
  スペーシングスケールを`globals.css`に導入して余白を統一した。検出結果は
  「N件見つかりました」という件数表示と、頭文字アバター付きのカードに変更した。
- **Excel(.xlsx)を`write-excel-file`で実装**: 当初CSVにBOMを付与すればExcelで
  開けると判断していたが、CEOの要望は実際の.xlsx形式だった。ライブラリ選定では
  `exceljs`（週間DL約1150万だが`tmp`/`archiver`等Node専用の依存を9個持ち、
  ブラウザ向けには別エントリポイントが必要で不要に重い）と比較し、
  `write-excel-file`（週間DL約56万だが依存1個のみ・ブラウザ専用設計・
  2026-06-08に最新版公開で活発にメンテナンスされている）を採用した。
  ダウンロード数は少ないが、ブラウザで完結するこのユースケースへの適合性を優先した。
  CSVと同じ数式インジェクション対策（`neutralizeFormula`）を多層防御として適用
  （xlsxは`type: String`で明示的に型付けされるためCSVほどの実害は無いはずだが、
  「メール送信者が自由に書ける値をそのまま渡す」という構造は同じため）。

## 2026-08-16: エラー監視にSentryを導入する（無料プラン）

`docs/specs/error-monitoring.md`の実装に伴う決定。P9に従い自分で判断し記録する。

- **Sentry Developerプラン（無料、5,000エラー/月、1メンバー）を採用**: このアプリの
  規模でエラー監視サービスを検討したところ、無料枠のみで十分と判断した。新規org作成時に
  14日間Business機能のトライアルが自動付与されるが、支払い情報は未登録のため
  期限後は自動的にDeveloperプランへ戻る（課金は発生しない）。
- **`tracesSampleRate: 0`でパフォーマンストレーシングは無効のまま**: 目的は未捕捉例外の
  検知のみ。トレーシング/セッションリプレイは別枠のクォータを消費し、かつ現時点で
  必要な機能ではないため意図的に有効化しない。
- **`SENTRY_AUTH_TOKEN`は未設定、ソースマップアップロードは今回スコープ外**:
  トークン発行にはSentry側の追加操作が要るが、無くてもビルド・送信は問題なく動く
  （圧縮後コードでスタックトレースが表示されるだけ）。必要になった時点で追加する。
  詳細は`docs/specs/error-monitoring.md`「満たせなかった条件」参照。
- **CSPの`connect-src`にDSNのホストを動的追加**: 既存のCSPは`connect-src 'self'`
  のみで、Sentryへのブラウザからの直接送信がブロックされることを実機で発見・修正した。
- **`dataCollection: { cookies: false, httpHeaders: false }`を明示指定**: 当初
  `sendDefaultPii`未設定（既定false）だけで済ませていたが、レビューで指摘の通り
  それはCookie/ヘッダーを名前ベースで一部除外するだけで全面的な非送信を保証しない。
  個人情報を送らない方針を挙動として保証するため明示的にオフにした。`Sentry.setUser()`
  も呼ばない。詳細は`docs/privacy-ops.md`に追記。
- **`app/privacy/page.tsx`の「第三者提供」を同じPRで更新**: レビューで指摘の通り、
  内部ドキュメント（`docs/privacy-ops.md`等）だけでは利用者は見られない。Sentryへの
  技術情報送信を公開ページ側にも明記した（JP-03: 公表事項の更新を別作業にしない）。
- **GitHub App連携を導入**: Sentry側でコミット帰属・スタックトレースへのコードリンクを
  出すための連携。対象リポジトリを本リポジトリのみに限定し、コードのAI学習利用や
  ブランチへの直接マージ権限は含まれない（Sentry側の権限説明画面で確認済み）。
- **`scripts/setup-sentry.sh`をリポジトリにコミットする**: アカウント作成・プロジェクト
  作成・DSN取得は人間の手動操作が必要なため、再現可能な手順として残す
  （`scripts/setup-google-oauth.sh`と同じ扱い）。

## 2026-08-14: Googleサインイン実装時の技術決定（まとめ）

`docs/specs/google-signin.md` の実装に伴う決定。P9に従い自分で判断し記録する。

- **認証ライブラリ**: `next-auth`（Auth.js）v5系（`5.0.0-beta.32`）。App Router向け実装
  がv5系にしかなく、SEC-50上ライブラリ利用が前提のため。betaは認識済み、追従予定。
- **アクセストークンは`jwt()`のみで保持し`session()`には含めない**: `session()`は
  `/api/auth/session`経由でブラウザに返るため、含めるとXSS時にトークンを窃取されうる。
  後続機能は`next-auth/jwt`の`getToken()`で直接読む。
- **`access_type=offline`+`prompt=consent`を付与**: `refresh_token`は初回同意時にしか
  発行されず、今つけないと後続機能で全ユーザーに再同意を強制することになる。
- **`trustHost: true`**: 配信ドメイン未確定で`AUTH_URL`未設定だと本番相当環境で
  `UntrustedHost`エラーになる（実測）。ドメイン確定後は`AUTH_URL`に移行する。
- **CSPのnonce移行は見送り、別PRに切り出す**: 2026-08-12の決定の見直し条件
  （認証機能追加）に該当したが、400行ルールに収めるため今回のPRには含めない。
- **`server-only`を依存に追加**: ARC-03が要求するimportだが`package.json`に無かった
  （`data/`ファイルがこれまで無く未検出だった）。VitestはNext.js固有の解決を持たず
  例外になるため、依存追加と`tests/setup.ts`でのモックが両方必要だった。
  `01_xxx`側の同じ抜けは別途検討。

## 2026-08-14: 技術判断を人間に振らない運用ルール（P9）を追加する

**背景**: 依頼者（CEO）は設計・実装・セキュリティの専門知識を前提にできない。
「これでいいですか」と技術的な選択肢を尋ねられても判断できず、かつ最終責任は
依頼者が持つという状況で、Googleサインイン機能の要件定義中、技術的な実装方法まで
依頼者に質問していたことが判明した。

**決定**: `rules/00-principles.md` に **P9** を新設した。人間に判断を仰ぐのは
「お金」「個人情報の取扱い方針」「機械判定できない最終確認・最終承認」の3種類だけとし、
それ以外の技術判断（ライブラリ選定、DAL/型設計、検出アルゴリズム等）はエージェントが
`rules/` を基準に自分で決め、`docs/decisions.md` に理由を記録する。人間に見せる前に、
`pnpm verify` とレビュー3体の Critical/High 指摘をすべて解消するまで自律的に繰り返す。
`rules/70-loop-engineering.md`（LOOP-04/05）、`.claude/agents/spec-writer.md`、
`docs/PLAYBOOK.md` をP9に合わせて更新した。テンプレート（`01_xxx`）にも同じ変更を適用済み。

**理由**: `00-principles.md` P6「人の注意力に依存しない」の応用。専門知識のない依頼者に
技術的な合否判定を委ねること自体が、機能しない基準になる。

## 2026-08-14: リポジトリを公開にして GitHub branch ruleset で main を保護する

**背景**: テンプレート（`01_xxx`）からサービス立ち上げ時、非公開リポジトリのままでは
GitHub branch ruleset が作成できない（Free プランは 403 で拒否される。Pro 以上が必要）。

**決定**: リポジトリを公開に変更し、`protect-main` ruleset（`pull_request`必須・
`deletion`禁止・`non_fast_forward`禁止）を作成した。公開前に、コミット履歴と
追跡ファイルにシークレット・認証情報が含まれていないことを確認済み
（`.env*`・鍵ファイルは元々 `.gitignore` 対象、コミットは初期テンプレートコミット1件のみ）。

**理由**: `00-principles.md` P6「人の注意力に依存しない。機械が落とせる形に変換する」に従い、
ローカルフック（`--no-verify`で回避可能）よりサーバー側の強制を優先する。

**`.githooks/pre-commit` は残す。** ruleset は「PRを経由すること」は強制するが、
ローカルの早期フィードバック（コミット前に気づく）の価値は別にあるため。

## 2026-08-12: CSP の `script-src` に `unsafe-inline` を許可する

**背景**: `checklists/release.md` SEC-92「`unsafe-inline` を避けている」を満たすため、
`next.config.ts` で `script-src 'self'` を試した。

**決定**: `script-src 'self' 'unsafe-inline'` を採用する。

**理由**: `next build && next start` の状態で Playwright を使って実測したところ、
`unsafe-inline` を外すと Next.js が RSC のペイロードを渡すために注入するインラインscriptが
CSP違反でブロックされ、ハイドレーションが壊れた（`React error #412`、コンソールにCSP違反2件）。
現時点ではペイロードに機微情報を含む機能（認証・決済等）が無いため、この妥協を許容する。

**見直し条件**: 認証や決済など、XSS経由のインラインscript実行が実害に直結する機能を追加する
タイミングで、`middleware.ts` によるnonceベースのCSPへ移行し、`unsafe-inline` を外す。
