# 全体像 — 何を基準にして、何が自動で守られるのか

このリポジトリで採用している**品質の考え方**と、**それを実際に動かしている仕組み**を説明します。
専門知識がなくても読めるように書いてあります。

---

## 1. そもそも何を解決しようとしているのか

AIにコードを書かせると、**書く速さは上がりますが、壊れる回数も増えます。**
これは調査でも裏付けられている現象で、原因は「AIが作る速さに、確認する側が追いつかない」ことです。

個人開発では、その確認をする人が**自分1人しかいません。**
つまり「気をつけて確認する」という方針は、いつか必ず破綻します。

そこでこのリポジトリでは、次の方針を採っています。

> **人の注意力に頼らない。機械が自動で止められる形に変換する。**

「ちゃんと確認しよう」ではなく、「確認しないと先に進めない仕組みにする」ということです。
駅の自動改札に近い発想で、切符を持っていない人は物理的に通れません。

---

## 2. 4つの層 — 誰が何を判断するか

品質チェックを、**コストの安い順**に4つの層に分けています。
これがこの仕組みの中心的な考え方です。

| 層    | 誰が見るか               | AIの費用 | 何を見るか                                   |
| ----- | ------------------------ | -------- | -------------------------------------------- |
| **1** | **機械**（自動チェック） | **ゼロ** | 型の矛盾、書式、テスト、セキュリティ設定など |
| **2** | 安いAI（レビュー担当）   | 小さい   | 変更部分だけを読んでレビュー                 |
| **3** | 高いAI（要件定義・設計） | 大きい   | 「何を作るか」「どう作るか」の判断           |
| **4** | **人間（あなた）**       | **ゼロ** | 画面の見た目、法務判断、最終承認             |

**大事な点: 機械と人間はAI費用がかかりません。**
だから「機械にできることは機械にやらせる」ことが、そのまま費用の節約になります。

AIを使うのは、**機械にはできず、かつ人間がやると大変なことだけ**に絞ります。

---

## 3. 品質基準 — 5つの関門（ゲート）

「できた」と言ってよい条件を、5段階に分けて定義しています。
**前の関門を飛ばして次に進みません。**

### G0 — 作り始める前

**何を作るのかを、作る前に文章にする。**

- 作る機能を**1文**で言えるか（言えないなら、まだ整理できていない）
- 「こういう状況で、こう操作したら、こうなる」を最低2本書く（うまくいく場合と、失敗する場合）
- 個人情報やお金を扱うか判定する
- 変更量が**400行以内**か（超えるなら2つに分ける）

書いた内容は `docs/specs/` にファイルとして保存します。
**会話の中だけにある計画は「決まった」と見なしません**（会話は消えるためです）。

### G1 — 作っている最中

**機械のチェックが全部通る。** 1つでも赤ければ、まだ「作業中」です。

`pnpm verify` という1つのコマンドで、以下がまとめて実行されます。

| チェック     | 何を見ているか                   |
| ------------ | -------------------------------- |
| typecheck    | 型（データの種類）の矛盾がないか |
| lint         | 危険な書き方をしていないか       |
| format:check | 書式が揃っているか               |
| test         | テストが全部通るか               |
| build        | 本番用に組み立てられるか         |

### G2 — 1つの機能ができた時点

**65項目の点検リスト**（`rules/checklists/feature.md`）を通します。
権限のチェック、テストの有無、エラー時の挙動などです。

### G3 — 公開する前

**67項目の点検リスト**（`rules/checklists/release.md`）を通します。
セキュリティ設定、日本の法令（プライバシーポリシー、特定商取引法など）、バックアップなど。

### G4 — 公開した後

実際に動かして確認し、30分間エラーを監視します。
異常があれば**まず元に戻してから**原因を調べます。

## 4. 何が自動で守られ、何が守られないのか

ここが一番大事な部分です。**正直に書きます。**

### 点検リスト132項目の内訳

| 分類               | 件数     | 割合    | 意味                                               |
| ------------------ | -------- | ------- | -------------------------------------------------- |
| **機械が見ている** | **25件** | **19%** | 自動で止まる。忘れようがない                       |
| まだ仕組みがない   | 30件     | 23%     | **今は誰も見ていない**。自動化できるはずだが未実装 |
| 人間が見るしかない | 74件     | 56%     | 画面の見た目、法務判断など。原理的に自動化できない |

**つまり、自動で守られているのは約2割です。**

これは弱点ですが、**隠さずに可視化していること自体が仕組みの一部**です。
「たぶん大丈夫」という曖昧な状態をなくし、
「誰も見ていない30件」がどれなのかをはっきりさせています。

未実装の30件は GitHub の課題（Issue #11〜#19）として登録済みで、
実装したら「機械が見ている」に移します。

### 実際に自動で動いているもの

**あなたのパソコンで動くもの**

- `pnpm verify` — 上記5種類のチェック
- コミット前のフック — `main`（本番の枝）への直接の書き込みを拒否

**GitHub上で自動で動くもの**（コードを提出すると勝手に走ります）

| 名前    | 内容                                                                           |
| ------- | ------------------------------------------------------------------------------ |
| verify  | 上記5種 + 脆弱性チェック + 依存の安全確認 + 変更量400行チェック + 設定の健全性 |
| headers | セキュリティ設定11項目を、実際にサーバーを起動して検査                         |
| e2e     | 本物のブラウザで3種類のテスト（表示・アクセシビリティ・スマホ幅）              |

**GitHub側の設定**

- `main` への直接の書き込みをサーバーが拒否（必ず提出→検査→統合の順を通す）

### 人間が見るしかない74項目

`rules/checklists/human.md` に**まとめてあります。**
リリースのたびに132項目を全部見るのは現実的でないため、
**機械のチェックが全部緑になってから、この74項目だけをまとめて確認する**運用です。

代表例:

- キーボードだけで操作を最後まで完了できるか
- バックアップから実際に復元できるか（試したことがあるか）
- プライバシーポリシーの記載と、実際にやっていることが一致しているか
- 本番で主要な操作を1回手で通したか

## 5. 費用（トークン）を抑える考え方

AIの利用料は「読んだ量 + 書いた量」で決まります。抑える方法は3つです。

**1. 機械にできることをAIにやらせない**

型の間違いをAIに探させると費用がかかりますが、`pnpm verify` は無料で確実です。
上の「4層」の考え方そのものが、費用対策になっています。

**2. レビュー担当を分け、変更部分だけを読ませる**

レビュー担当のAIには、**変更した部分だけ**を渡します。
リポジトリ全体を読ませません。また、レビュー担当は安いモデルを使い、
**ファイルを書き換える権限を与えていません**（読むだけ）。無駄なやり取りが発生しません。

**3. 1つの作業を小さく保つ**

変更量400行の制限は、レビューしやすさのためだけでなく、
**1回の作業を1回の会話で終わらせる**ためでもあります。
会話が長引くほど、AIは過去のやり取りを読み返すことになり、費用が増えます。

## 6. 正直な弱点

| 弱点                           | 現状                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| 自動化率が19%しかない          | 30項目が未実装。Issue #11〜#19 で追跡中                       |
| まだ機能を1つも公開していない  | 基準だけが先行している状態。実際に使うと重すぎる可能性がある  |
| 人間が見る74項目は結局は人頼み | `human.md` にまとめて負担を減らしてはいるが、なくせてはいない |
| エラー監視サービスが未選定     | G4の「30分監視」を自動化できていない                          |

**基準を完璧にしてからコードを書く、という順序自体に無理があります。**
実際に機能を1つ作ってみて、重すぎる部分は削るのが健全です。

## 7. 用語集

| 用語                     | 意味                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------- |
| **ルーブリック**         | 合格基準表。学校の採点基準のようなもの。`rules/` にある                                 |
| **MUST / SHOULD**        | 「絶対に守る」／「できれば守る（守らないなら理由を書く）」                              |
| **G0〜G4**               | 5つの関門。上の第3節を参照                                                              |
| **リポジトリ**           | プログラムとその変更履歴の保管庫。GitHubに置いてある                                    |
| **main（メイン）**       | 本番用の枝。ここが常に正常な状態を保つ                                                  |
| **PR（プルリクエスト）** | 「この変更を取り込んでよいか」の提出。検査が全部通らないと統合できない                  |
| **CI**                   | 提出のたびにGitHubが自動で走らせる検査                                                  |
| **テスト**               | プログラムがプログラムを検査する仕組み。人が毎回手で確認しなくて済む                    |
| **E2E テスト**           | 本物のブラウザを動かして、利用者と同じ操作で確認するテスト                              |
| **DAL**                  | データの出入口を1箇所に集めた場所。「誰がどのデータを見てよいか」の判定をここだけで行う |
| **DTO**                  | 画面に渡す用に、必要な項目だけに絞ったデータ                                            |
| **lint（リント）**       | 危険な書き方や書き癖を機械が指摘する仕組み                                              |
| **ハーネス**             | AIが安全に動くための土台（検査・制限・記録の仕組み全体）                                |
| **ループ**               | AIが「作業→検査→まだなら再挑戦」を、条件を満たすまで自動で繰り返すこと                  |
